---
title: Management panel
---

The engine can serve a management UI itself, so a self-hosted deployment gets one without running a
separate admin application. It is disabled by default.

:::note[Available since 2.2]
The panel is being built module by module. Today it serves the application shell; sign-in and the
management modules land in following releases.
:::

## Enabling it

```bash
CONTEMBER_PANEL_ENABLED=true
CONTEMBER_PANEL_PATH=/panel   # optional, this is the default
```

Or in `config.yaml`:

```yaml
server:
  panel:
    enabled: true
    path: /panel
```

With the flag off, the panel path returns the same `404 Route not found` as any other unknown path —
an engine with the panel disabled is indistinguishable from one that never had it.

## What gets served

The panel is a single-page application bundled into the engine binary: there is no directory to
mount, no extra image, and no version skew between the UI and the API it talks to. Everything under
the configured path is served from that bundle — content-hashed assets are served immutable, and any
other path returns the application shell so client-side routing works.

The panel's own API traffic lives directly under the same path (`/panel/api`), on the same origin as
the page, so there is no CORS setup and no separate host to configure.

:::caution[Put it behind the same protection as your API]
The panel is served from the engine's HTTP port. If that port is public, so is the panel's login
page. It is served with `frame-ancestors 'none'`, `noindex` and a restrictive Content-Security-Policy,
but the usual network-level protections you apply to the API apply here too.
:::

## Who may sign in

Enabling the panel decides whether it is served at all. Who may enter it is part of the **tenant
configuration**, not of the deployment environment:

```ts title="tenant.config.ts"
config: {
  panel: {
    globalRoles: ['super_admin'],
    projectRoles: ['admin'],
  },
}
```

An identity may enter when one of these holds:

- one of its global roles (`identity.roles`) is listed in `globalRoles`, or
- it has a membership with one of `projectRoles` in **at least one** project.

The defaults are `globalRoles: ['super_admin']` and `projectRoles: ['admin']`. An empty list closes
that dimension; both empty means nobody can enter.

See [declarative configuration](/reference/engine/tenant/declarative-config) for how to apply this,
or set it with the [`configure`](/reference/engine/tenant/configuration) mutation directly.

:::note[This is an entry gate, not authority]
Being allowed into the panel grants no rights. Every action taken inside it goes through the same
tenant API and the same ACL as any other client, so a user only ever sees and changes what their
roles and memberships already permit. Widening these lists opens the door; it does not hand out
permissions.
:::

## Building from source

The panel assets are generated into the server bundle by `pre-build`. When you build the engine
yourself, `scripts/server-build/run.sh` takes care of it; if you invoke `bun build` or run the engine
straight from source, run `bun run --filter=@contember/engine-panel pre-build` first. Without the
assets the engine still starts, logs that the panel is enabled but unbuilt, and does not serve it —
a released build cannot end up in that state, because the asset build fails when it produces nothing.
