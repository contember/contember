---
title: Profile and password changes
---

Two pairs of mutations let persons (and administrators) update profile and credentials:

| Self-service | Admin |
|---|---|
| `changeMyProfile(email, name, currentPassword, otpToken)` | `changeProfile(personId, email, name)` |
| `changeMyPassword(currentPassword, newPassword)` | `changePassword(personId, password)` |

The self-service variants require the caller to be authenticated as the person being changed; the admin variants take a `personId` and are gated by per-target permission checks.

## Self-service

### Change my profile

```graphql
mutation {
  changeMyProfile(email: "new@example.com", name: "Alice Example") {
    ok
    error { code developerMessage }
  }
}
```

Pass either field individually — omitted fields are left unchanged. Setting `name: ""` clears the name.

:::note[E-mail-change verification — opt-in *(since 2.2)*]
When `emailChange.requireVerification` is enabled (it is **off** by default) — or the account was created under sign-up verification, which implies it — changing the e-mail does **not** apply immediately: `changeMyProfile` returns `ok: true`, mails a confirmation token to the *new* address, and keeps the old address active until the user confirms via [`confirmEmailChange`](/reference/engine/tenant/email-verification#e-mail-change-verification). A `name` change passed in the same call is still applied right away. When neither applies (a deployment with no verification at all), addresses swap immediately as before. In that direct case the change also clears the verified status of the address, since the new one is unproven.
:::

#### Re-authentication for an e-mail change

:::note[Available since 2.2]
With `emailChange.requireReauthentication` enabled (it is **off** by default), a session alone is not enough to change the e-mail address. The caller passes its current password or a current TOTP code:

```graphql
mutation {
  changeMyProfile(email: "new@example.com", currentPassword: "…") {
    ok
    error { code }
  }
}
```

- The check applies to both the direct change and the verified one (before the confirmation token is mailed). A `name`-only change needs no re-authentication.
- After a direct change, a notice goes to the old address and every other session of the person is disabled; the session that made the change stays signed in. Unused tokens of the person (password reset, passwordless) are marked as used.
- A person with neither a password nor TOTP, typically one signed up through an identity provider, cannot change its own e-mail while the option is on. An administrator can still change it with `changeProfile`.
- Failed checks are recorded as a failed `email_change` in the [audit log](/reference/engine/tenant/audit-log).
- A person gets at most 5 re-authentication attempts within 15 minutes, shared with the [MFA changes](/reference/engine/tenant/two-factor); further attempts answer `RATE_LIMIT_EXCEEDED`, even with the right credential.

With the option off, `currentPassword` and `otpToken` are ignored and `changeMyProfile` behaves as before.
:::

Errors:

| Code | Cause |
|---|---|
| `NOT_A_PERSON` | Caller is authenticated via a permanent API key, not a person. |
| `INVALID_EMAIL_FORMAT` | Email failed format validation or has whitespace inside (whitespace around it is ignored). |
| `EMAIL_ALREADY_EXISTS` | Email is already used by another person. |
| `RATE_LIMIT_EXCEEDED` | *(since 2.2)* Per-recipient backoff on confirmation mails for a verified e-mail change, or more than 5 re-authentication attempts of the person within 15 minutes. |
| `REAUTHENTICATION_REQUIRED` | *(since 2.2)* `emailChange.requireReauthentication` is on and neither `currentPassword` nor `otpToken` was passed. |
| `INVALID_PASSWORD` | *(since 2.2)* `currentPassword` does not match. |
| `INVALID_OTP_TOKEN` | *(since 2.2)* `otpToken` is not a current TOTP code of the person. |

An immediate (unverified) email change records `email_change` in the [audit log](/reference/engine/tenant/audit-log); a verified change records `email_change_init` / `email_change_complete` instead.

### Change my password

```graphql
mutation {
  changeMyPassword(currentPassword: "…", newPassword: "…") {
    ok
    error {
      code
      weakPasswordReasons
      developerMessage
    }
  }
}
```

The caller must supply their current password — this protects against session hijack where an attacker holding a session token tries to lock out the user.

Errors:

| Code | Cause |
|---|---|
| `NOT_A_PERSON` | Caller is authenticated via a permanent API key. |
| `NO_PASSWORD_SET` | The person has no password (IDP-only / passwordless-only). Use [password reset](/reference/engine/tenant/password-reset) to *set* the first password. |
| `INVALID_PASSWORD` | `currentPassword` is wrong. |
| `TOO_WEAK` | `newPassword` failed [password policy](/reference/engine/tenant/password-policy). `weakPasswordReasons[]` carries reasons including `COMPROMISED` *(since 2.2)*. |

A successful change records `password_change` in the audit log.

## Admin

### Change someone's profile

```graphql
mutation {
  changeProfile(personId: "…", email: "new@example.com", name: "Alice") {
    ok
    error { code developerMessage }
  }
}
```

Gated by `PERSON_CHANGE_PROFILE` against the *target's* roles — a `PROJECT_ADMIN` can change profiles of persons whose roles do not exceed their own; `SUPER_ADMIN` is unrestricted.

Errors: `PERSON_NOT_FOUND`, `INVALID_EMAIL_FORMAT`, `EMAIL_ALREADY_EXISTS`.

The admin `changeProfile` is **never** routed through [e-mail-change verification](/reference/engine/tenant/email-verification#e-mail-change-verification) — the new address is applied immediately regardless of `emailChange.requireVerification`. Only the self-service `changeMyProfile` goes through confirmation.

### Set someone's password

```graphql
mutation {
  changePassword(personId: "…", password: "…") {
    ok
    error {
      code
      weakPasswordReasons
      developerMessage
    }
  }
}
```

Gated by `PERSON_CHANGE_PASSWORD` against the target's roles. No current-password check — the admin is trusted by policy.

Use cases:

- Forced credential rotation after a known compromise.
- Setting a temporary password before invoking [`forceSignOutPerson`](/reference/engine/tenant/sessions#admin-force-sign-out) to lock the person out of their existing sessions.
- Bulk migration scripts.

The new password is validated against the active [password policy](/reference/engine/tenant/password-policy) just like the self-service path. Records `password_change` in the audit log.

## When the person has no password

`changeMyPassword` returns `NO_PASSWORD_SET` for persons created via IDP or passwordless-only flows. To set an initial password, either:

- Trigger the public [password reset](/reference/engine/tenant/password-reset) flow.
- Have an admin call `changePassword` directly.

*(since 2.2)* Neither helps a person linked to an identity provider with [`disableLocalAuthentication`](/reference/engine/tenant/idp#idp-only-authentication): `signIn` refuses their password with `IDP_REQUIRED` and the reset mail is not sent.
